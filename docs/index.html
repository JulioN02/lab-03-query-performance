02 La herramienta: EXPLAIN ANALYZE

Para entender qué está ocurriendo dentro de la base de datos, podemos usar EXPLAIN ANALYZE como una brújula: no solo muestra el plan que PostgreSQL considera, sino que ejecuta la consulta y muestra el plan que realmente usó.

Aquí se determina — scan · filtro · sort · join · agregación

  • Costo estimado vs ejecución real — lo que el planificador predijo contra lo que pasó.
  • Filas leídas — cuántas filas tuvo que tocar realmente para responder.
  • Filas descartadas — las que leyó y descartó (el trabajo invisible de una consulta).
  • Dónde se gasta el tiempo — en qué nodo del plan se va el tiempo real.
código de la función real
1// Un ejemplo de lo que hace EXPLAIN ANALYZE en la consulta
2export async function explainAnalyze(text: string): Promise<string> {
3 const result = await pool.query(`EXPLAIN ANALYZE ${text}`);
4 return result.rows.map((row: any) => row['QUERY PLAN']).join('\n');
5}
EXPLAIN ANALYZE ejecuta la consulta de verdad. Por eso los números de la derecha (actual time, rows= reales, loops=) son los hechos, y los de la izquierda (cost=, rows= estimados) son solo la estimación del planificador. Lo importante no es cuánto tarda la consulta, sino qué trabajo tuvo que realizar para producir ese resultado.

Sin un índice en category, PostgreSQL no tiene forma de saltar filas: ejecuta un sequential scan y lee las 10.000.000 de filas una por una, descartando las que no coinciden. Un SELECT * que devuelve solo 1M de filas paga por leer las otras 9M que descarta. El problema no es que PostgreSQL lea datos, es cuánto trabajo necesita realizar para encontrar lo que realmente necesita: el tiempo crece linealmente con el tamaño de la tabla (O(n)) — 5.5 segundos y 5037.52 ms de Execution Time.

03 Posibles soluciones al problema

Si el problema es el plan de ejecución, la solución es que PostgreSQL haga menos trabajo mediante índices, pero no cualquier índice: su utilidad depende de los datos, de la consulta y de la cantidad de filas que cumplen el filtro. Estas son las posibles soluciones, de la más simple a la más sofisticada, cada una con su plan resultante y sus números medidos.

(a) Sin índice: Sequential Scan

Sin índice en category, PostgreSQL no tiene forma de localizar las filas: lee la tabla fila por fila, aplica el filtro a cada una y conserva solo las que cumplen la condición. Es el plan de los 5037.52 ms de la sección 02 — el punto de partida de todo el problema.

1 · Seq Scan (10M filas)→ 2 · 9M descartadas→ 3 · ~5.5 s

(b) El índice B-Tree: Antes/Después — Lección de Selectividad ⚠️ 1.3X · BAJA SELECTIVIDAD

El índice B-tree es la estructura de índice por defecto de PostgreSQL: un árbol balanceado que ordena los valores de category y permite localizar las filas coincidentes sin recorrer la tabla. Pero elegir un índice "por si acaso" no es gratis, y este experimento lo demuestra: la misma consulta antes y después de crear el índice, midiendo el cambio de plan. La lección incómoda es la primera: como category tiene baja selectividad (~1M de 10M = 10%), el tiempo pasa de 5547.21 ms a 4399.28 ms — solo 1.3x.

medido5547.21 → 4399.28 ms1.3x · 20.7% reducción

(c) Índice compuesto: Reporte GROUP BY ✅ 4.6X · INDEX ONLY SCAN

Las consultas de reporte no piden SELECT *: agrupan (GROUP BY), agregan (AVG, COUNT) y ordenan. Ahí el juego cambia: un índice compuesto reúne varias columnas en una misma estructura para adaptarse a ese patrón de acceso. Si el índice contiene todas las columnas que la consulta necesita, PostgreSQL puede responder sin volver a la tabla — un Index Only Scan. Este experimento compara el reporte sin índice (1917.99 ms), con índice simple (1856.86 ms, un no-op 1.0x) y con índice compuesto (category, value) (414.01 ms = 4.6x).

(d) Índice cubriente: Responder sin volver a la tabla ✅ 2.9X · SIN HEAP

Para la misma consulta de reporte, el índice cubriente (category, value, id) logra un Index Only Scan puro: contiene todas las columnas que la consulta necesita y responde sin volver a la tabla. Y hay un bonus anti-intuitivo: el índice simple salió 0.8x — más lento que no tener nada. La evidencia desmiente "más índices = más rápido": un índice puede mejorar una consulta, no producir cambios relevantes o incluso hacerla menos eficiente.

06 ¿Por qué el índice simple fue 0.8x (más lento)?

El plan Bitmap Heap Scan construyó el bitmap (Bitmap Index Scan: 399 ms) y después tuvo que volver al heap por value, con recheck de ~1.1M filas. Pagó el costo del índice y el costo de la tabla. La consulta pedía AVG(value): sin value en el índice, el índice no cubre la consulta.

1 · Bitmap Index Scan → 399 ms→ 2 · vuelve al heap por value→ 3 · recheck ~1.1M filas→ 4 · 3236.70 ms > 2531.10 ms (0.8x)

07 Cuánto importa la consulta (y no el índice "por si acaso")

El mismo índice B-tree dio 1.3x para SELECT * (exp 2) y 4.6x / 2.9x para el reporte agregado (exp 3-4). La pregunta no es qué índice agregar, sino qué trabajo realiza PostgreSQL y qué estructura puede reducirlo. El índice correcto surge de leer la consulta: qué columnas filtra, cuáles selecciona y qué fracción de la tabla devuelve (selectividad). El índice se elige después de leer el plan, nunca "por si acaso".

La misma consulta decide el índice

  • SELECT * (exp 2) → muy poco que ganar con un índice simple: el SELECT * obliga a volver al heap · 1.3x.
  • Reporte agregado (exp 3) → si el índice cubre el WHERE + SELECT, Index Only Scan · 4.6x.
  • Solo columnas del índice (exp 4) → Index Only Scan puro · 2.9x.

El flujo correcto

1 · lee la consulta→ 2 · ejecuta EXPLAIN ANALYZE→ 3 · decide el índice

Nunca al revés. El índice no se elige "por si acaso": se elige por la consulta que realmente corre.

08 Los 6 axiomas del rendimiento

Estos son los principios que guían todo el laboratorio. Cada experimento los pone a prueba con datos medidos — y algunos (como el Axioma 3) revelan sus matices cuando la selectividad es baja.

01

Mide antes de optimizar

"Nunca optimices una consulta sin ver su plan de ejecución primero."

EXPLAIN ANALYZE es el punto de partida, no el final. El plan muestra dónde se gasta el tiempo: scan, filtro, sort, join. Compara lo que el planificador estimó frente a lo que realmente pasó, dónde se concentra el trabajo y cuántas filas se descartaron. Las estimaciones pueden estar desactualizadas si no se ejecuta ANALYZE tras cargar datos.

Regla: si no mediste el problema, no sabes qué estás optimizando.
02

El plan de ejecución es la verdad

"No confíes en tu intuición sobre cómo PostgreSQL ejecuta una consulta — confía en el plan."

PostgreSQL elige el plan según estadísticas y costos estimados. A veces elige mal (estadísticas viejas, datos sesgados). EXPLAIN ANALYZE ejecuta la consulta y muestra el plan real ejecutado.

Regla: el plan es tu brújula — léelo antes de decidir cualquier cambio.
03

Un índice es una inversión

"Un índice bien elegido puede transformar una consulta de segundos a milisegundos."

Sin índice = sequential scan (O(n)). Con B-tree = index scan (O(log n)). Pero cada índice paga costo de escritura (INSERT/UPDATE/DELETE más lento) y depende de la selectividad del filtro — lo vimos en vivo en el Exp 2 (1.3x).

Regla: no se trata de tener más índices, sino de elegir los necesarios y medir su impacto.
04

El tamaño de los datos importa

"Lo que funciona con 100k filas puede ser inaceptable con 10M filas."

El sequential scan crece linealmente con la tabla; el index scan crece logarítmicamente (prácticamente constante). La prueba con 100k filas no representa al sistema real si en producción hay 10M.

Regla: mide con el volumen de datos realista, no con el que tienes ahora.
05

Repetibilidad > casualidad

"Una medición aislada no vale nada — la ciencia requiere repetición."

La caché del sistema y de PostgreSQL puede confundir la medición. La primera corrida suele ser la más lenta (caché fría) — descártala. Este lab repite cada experimento y reporta rangos (p. ej. 4778.97 – 5936.61 ms).

Regla: una medición muestra un resultado; varias muestran una tendencia.
06

El índice correcto depende de la consulta

"No existe un índice ideal para todas las consultas — existe el índice correcto para la tuya."

B-tree para equality/rangos · compuesto para consultas que filtran por varias columnas · cubriente para evitar accesos adicionales a la tabla (index-only scan). Lo vemos en vivo en los Exp 3 y 4 — y en el caso B, que fue 0.8x más lento.

Regla: elige el índice según el patrón de consulta, no "por si acaso".

09 Conclusiones

Tres preguntas que este laboratorio responde con números: cuándo indexar, qué índice elegir y cómo leer el plan.

Cuándo indexar

Mide primero (Axioma 1): ejecuta EXPLAIN ANALYZE y observa si el nodo de scan es Seq Scan sobre una tabla grande. Indexa las consultas frecuentes sobre datos que crecen, y observa la selectividad del filtro: si devuelve el 10% de la tabla (como category), el índice apenas ayuda (1.3x) — la mejora real aparece cuando el filtro es selectivo o el índice cubre la consulta (4.6x).

Qué índice elegir

Simple (category): equality y devuelve pocas filas. Compuesto (category, value): filtros + agregación/orden — cubre el WHERE + SELECT del reporte. Cubriente (agrega id): responde 100% desde el índice (Index Only Scan) en modo solo de lectura, sin volver al heap. Cada columna extra = más espacio en disco y más costo de escritura.

Cómo leer el plan

Lea de adentro hacia afuera (el nodo de scan primero). Compare estimado vs real (cost=, rows= vs actual time, rows=); si difieren mucho, ejecuta ANALYZE. Observa Rows Removed by Filter: alto = se está descartando muchísimas filas. Index Cond verde = el índice resuelve el filtro. Execution Time y actual time del nodo de scan = dónde se va el tiempo.

10 Glosario

Los términos que usa este laboratorio, en una tabla: qué son y dónde aparecen en un plan.

TérminoDefiniciónCómo verlo en el plan
EXPLAIN ANALYZE Ejecuta la consulta de verdad y muestra el plan real: métodos de acceso, filas reales y tiempos por nodo. Sin ANALYZE solo estima, no ejecuta. actual time · Execution Time
Sequential Scan (Seq Scan) Lee toda la tabla fila por fila en orden físico (O(n)). Se elige cuando no hay índice útil o se va a devolver gran parte de la tabla. Rows Removed by Filter alto
Index Scan Usa un B-tree para localizar las filas coincidentes y va al heap a buscarlas (O(log n) + I/O selectivo). Index Cond
Index Only Scan El índice contiene todas las columnas del WHERE + SELECT: responde sin volver a la tabla (exp 3 y 4). Heap Fetches bajo
Bitmap Scan Dos nodos: Bitmap Index Scan construye un mapa de bits de páginas y Bitmap Heap Scan lee del heap solo esas páginas. Ideal cuando el filtro devuelve muchas filas. Bitmap Index Scan + Index Recheck
Selectividad Qué fracción de la tabla devuelve el filtro (1M/10M = 10%). Baja selectividad = devuelve mucho → el índice simple ayuda poco (1.3x). rows= vs total
Cardinalidad (rows=) Filas estimadas por el planificador, basadas en las estadísticas. Si difieren mucho de las reales, ejecute ANALYZE. rows=1004684 vs rows=1000000
ANALYZE Actualiza las estadísticas del planificador. Obligatorio después de cargar datos o crear índices. ANALYZE large_table;
Costo estimado (cost=) Unidad abstracta del planificador (mezcla de I/O y CPU) para comparar planes. No es tiempo. cost=0.00..211385.14
Filas estimadas vs reales La estimación (rows=) contra lo que realmente pasó (actual rows=). Diferencias grandes = estadísticas viejas. 1004684 est. vs 1000000 real
Rows Removed by Filter Filas leídas y descartadas por el filtro en un scan. Alto = la consulta paga por leer filas que no devuelve. Rows Removed by Filter: 9000000
Heap Fetches Visitas al heap desde un Index Only Scan (filas no visibles). Con VACUUM al día tiende a 0. Heap Fetches: 71010
Index Recheck Re-verificación del filtro al leer el heap (bitmaps lossy). Trabajo extra tras el índice. Rows Removed by Index Recheck: 3440885
Covering index (cubriente) Índice que incluye las columnas del SELECT además de las del WHERE → habilita el Index Only Scan. CREATE INDEX … ON large_table(category, value, id)
B-tree Árbol balanceado, el índice por defecto de PostgreSQL. Ideal para equality y rangos. CREATE INDEX … USING btree
O(n) vs O(log n) Cómo crece el costo con el tamaño de la tabla: el sequential scan lee todo (lineal), el index scan salta niveles (logarítmico, casi constante). 10M filas: ~5.5s vs ~400ms
Planning Time vs Execution Time Cuánto tardó el planificador en elegir el plan vs cuánto tardó la consulta en ejecutarse. El tiempo de verdad se va en el segundo. Planning Time: 2.154 ms · Execution Time: 5037.520 ms
